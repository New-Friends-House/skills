# Deps Update

## 1. 현재 리포 조회

1. 현재 작업 디렉터리에서 리포 루트, 적용되는 `AGENTS.md`, Git 상태를 확인한다. 이 경로의 manifest, workspace 설정, lockfile을 기준으로 한다. 이전 대화의 경로·버전·후보 목록을 재사용하지 않는다.
2. pnpm 버전과 사용할 명령의 `--help`를 확인하고, 조회 범위에 모든 활성 workspace와 루트를 포함한다.
3. 각 활성 프로젝트의 `dependencies`, `devDependencies`, `optionalDependencies`를 모아 외부 직접 의존성을 중복 제거한다. 내부 `workspace:` 의존성은 제외한다. catalog 참조는 workspace 설정으로, 현재 버전은 lockfile의 importer별 해석 버전으로 해결한다. pnpm lockfile이 YAML 여러 문서로 구성되면 애플리케이션 importers가 있는 문서를 찾는다.
4. 모든 외부 직접 의존성에 대해 설정된 레지스트리를 직접 조회하고 lockfile의 현재 버전과 비교한다. 일반 패키지는 `dist-tags`, 안정 버전 여부, 배포 시각을 확인하고, 범위 제한이 있는 패키지는 전체 `versions`에서 허용 버전을 찾는다. 인증이 필요한 레지스트리는 기존 설정을 사용하되 토큰과 설정 원문을 출력하지 않는다.
5. overrides, 버전 지정 patches, engines, peerDependencies, release-age 및 build-script 정책을 확인한다. release-age는 명시된 설정과 현재 pnpm 버전의 기본값을 함께 확인한다. 최신 버전이 대기 시간에 걸리면 정책을 충족하는 이전 안정 버전을 목표로 제시하고 최신 버전은 보류한다. 최신 버전이 있다는 사실과 현재 리포에서 설치·사용 가능한지를 구분한다. 조회 오류가 있는 패키지는 최신이라고 단정하지 않는다.
6. Expo가 있으면 관련 Expo 스킬을 읽고 lockfile에 해석된 **현재 Expo 버전**의 `bundledNativeModules.json`과 각 직접 의존성을 비교한다. 설치된 매핑 파일이 없으면 해당 정확한 Expo 버전의 공식 레지스트리 배포 tarball에서 매핑을 읽는다. SDK 호환 범위, npm 최신 버전, 현재 버전 및 `expo.install.exclude` 예외를 구분한다. 매핑에 없는 모바일 패키지는 현재 React·React Native·관련 native 패키지의 peer 요구사항을 별도로 확인하고, 확인되지 않은 후보는 보류한다. 검증이 허용되고 로컬 Expo CLI가 설치돼 있으면 Expo 앱 디렉터리에서 `CI=1 EXPO_NO_TELEMETRY=1 pnpm expo install --check`를 실행한다. source-only 모드이거나 로컬 의존성이 없으면 매핑 비교까지 수행하고 로컬 검사 미실행 사유를 명시한다. 조회를 위해 의존성을 설치하거나 `--fix`를 실행하지 않는다. 이 조회에 앱 실행이나 기기 연결은 필요하지 않다.

이 단계에서는 manifest, lockfile, patches 및 설치된 의존성을 변경하지 않는다. 필요하면 조회 결과를 리포 밖 임시 파일에 저장한다. 워크스페이스 밖 프로젝트와 간접·peer-only 의존성은 기본 집계에서 제외하고 범위를 명시한다.

조회 완료 기준은 전체 직접 의존성의 레지스트리 조회와 현재 버전 비교, Expo가 있는 경우 현재 SDK 매핑 비교를 모두 수행한 것이다. 각 확인의 실행 여부, 오류·미실행 사유, 보류 이유를 후보 목록과 함께 짧게 보고한다. 이 읽기 전용 조회는 스킬 호출에 포함되며 repo-wide 검증이나 앱 실행과 구분한다. 일부 조회가 막혀도 독립적으로 가능한 확인은 계속하고, 확인하지 못한 항목을 완료로 보고하지 않는다.

## 2. 번호를 붙여 선택 요청

실제로 진행할 수 있는 후보를 아래 우선순위로 정렬하고 **연속된 번호 1, 2, 3, 4, ...**를 붙인다. 같은 우선순위 안에서는 패키지 이름순으로 정렬한다.

1. 기존 호환 범위의 패치 업데이트.
2. 일반 웹·공유 라이브러리의 마이너 업데이트.
3. 인증·데이터·에디터 등 동작 영향이 큰 업데이트.
4. SDK 호환성이 확인된 모바일 업데이트.
5. 마이그레이션 범위가 확인된 메이저 업데이트.

버전을 함께 맞춰야 하는 패키지는 한 번호로 묶는다. 예: Better Auth 본체/core/expo, Lexical 본체/관련 패키지, React/React DOM/타입, Prisma CLI/client/adapter. 각 그룹의 **모든 직접 변경 대상**과 각 목표 버전을 보여준다. 단순히 같은 공급자의 패키지라는 이유만으로 묶지 않는다.

번호별로 다음 정보를 제시한다.

| 번호 | 패키지 또는 함께 업데이트할 그룹 | 현재 → 목표 | 영향·주의점 |
| --- | --- | --- | --- |
| 1 | 실제 조회한 패키지 | 실제 버전 → 허용된 목표 버전 | 사용하는 앱·패키지와 필요한 작업 |

SDK 비호환, 정책 제한, prerelease 또는 해결되지 않은 호환성 문제로 진행할 수 없는 패키지는 **번호 없는 보류 목록**에 이유와 함께 표시한다.

마지막에 `업데이트할 번호를 골라주세요. 예: 1,2,4`라고 안내하고 **사용자 답변을 기다린다.** 현재 사용자의 요청이 조회뿐이면 업데이트를 시작하지 않는다. 제시한 리포 경로와 `번호 → 패키지·현재 버전·목표 버전·그룹 구성` 매핑을 대화에서 유지한다.

## 3. 선택한 번호 업데이트

- `1,2,4`, `1 2 4` 등 명확한 번호 목록을 해석하고 중복을 제거한다. 이 응답은 **그 번호에 미리 표시한 대상과 목표 버전의 업데이트 승인**이다. 다시 확인을 요청하지 않고 진행한다. “전부”는 선택 가능한 번호 전체를 뜻한다.
- 다른 목적의 숫자를 선택으로 추정하지 않는다. 없는 번호, 불명확한 범위 또는 번호 매핑을 잃은 경우에만 필요한 확인을 요청한다. 리포 경로가 바뀌었다면 이전 번호를 새 리포에 적용하지 않는다.
- 현재 Git 상태와 선택 대상의 manifest·lockfile·정책을 다시 확인한다. 표시 이후 최신 버전이 더 나왔어도 **표시한 목표 버전**을 사용한다. 다른 작업으로 이미 업데이트됐으면 상태를 보고하고, 선택을 실질적으로 바꾸는 변경이 있으면 해당 항목만 다시 선택받는다.
- 선택한 패키지의 릴리스 노트와 호환 요구사항을 확인한다. 기존 patch가 있으면 수정 내용이 upstream에 반영됐는지 확인하고 필요한 patch만 재적용한다. 실제 적용 전에 기존 리포가 요구하는 계획 문서를 작성한다. 번호 목록만으로 미해결 설계나 SDK 비호환을 해결된 것으로 취급하지 않는다.
- `catalog:` 사용 패키지는 catalog의 실제 버전을 수정하고 참조를 유지한다. 같은 catalog를 사용하는 호출자는 함께 영향을 받는다고 보고한다. 개별 manifest의 exact/caret/tilde 정책과 override의 원래 목적을 유지하며 **선택한 직접 의존성만** 수정한다. 필수 동반 직접 의존성이 최초 그룹에 없었다면 이유를 설명하고 그 추가 항목만 선택받는다.
- 현재 pnpm과 리포 API로 의존성을 설치하고 하나의 workspace lockfile을 갱신한다. 구조화된 JSON/YAML 편집과 shell 인자를 사용한다. 선택하지 않은 직접 의존성을 함께 올리는 `update --latest` 일괄 실행이나 lockfile 전체 재생성을 피한다. 해결 과정에서 생기는 필요한 간접 의존성 변경은 검토하고 보고한다.
- 설치 스크립트가 리포에서 승인하지 않은 lint/fix/typecheck/검증을 자동 실행한다면 `--ignore-scripts` 등으로 그 실행을 피하고, 설치에 필요한 허용된 패키지 lifecycle만 좁게 처리한다. 필요한 산출물을 만들지 못하면 설치 완료로 보고하지 않는다. 레지스트리·release-age·build-script 정책을 임의로 완화하지 않는다.
- 패키지 API 변경으로 필요한 사용처 수정까지 완료한다. 기존 미커밋 작업을 보존한다. DB 마이그레이션, 데이터 직접 변경, 배포, 커밋 또는 push는 이 선택에 포함되지 않는다.

## 4. 완료 확인과 보고

설치 결과, 선택 대상의 최종 해석 버전, 관련 manifest·catalog·override·patch 및 lockfile diff를 검토한다. 선택 밖 직접 의존성이 의도치 않게 변경됐으면 관련 변경만 복구한다. 설치 실패 시 선택 대상의 허용 범위에서 원인을 해결하고, 해소할 수 없는 블로커와 남은 파일 상태를 구체적으로 보고한다.

`AGENTS.md`와 현재 대화의 검증 범위를 따른다. 이 스킬이나 번호 선택만으로 repo-wide fix/typecheck, standalone lint, 테스트 추가 또는 빌드를 승인하지 않는다. Sena Note의 `pnpm run fix`와 `pnpm run typecheck`는 사용자의 명시적 `/check` 또는 `$check`에만 실행한다. 모바일 native 변경은 새 native 빌드와 물리 기기 확인이 필요한 경계를 밝혀야 하며, 설치 성공을 런타임 성공으로 표현하지 않는다.

최종 응답에는 선택한 번호별 `패키지: 이전 → 최종 버전`, 변경한 파일, 실제 수행한 확인, 미실행 검증, 보류·실패 항목을 짧게 적는다. 조회만 했다면 후보 목록과 선택 안내로 끝낸다.
